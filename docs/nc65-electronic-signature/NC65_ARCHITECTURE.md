# NC65 扩展架构

## 原平台调用与新增层

原调用主线为 NC 原生客户端动作 → NCLocator 远程服务/PF 流程 → 业务动作/BP/规则 → BaseDAO/平台持久化。新增电子签名处于原业务动作前；业务审计处于真实服务端业务事务中。

新增源码保留 `src/client`、`src/public`、`src/private` 三层：

- public：序列化的操作上下文、策略和签名结果，以及远程服务接口；不得依赖客户端 Swing 类。
- client：UIDialog 签名窗口、ActionInterceptor、模型/节点适配、策略及日志查询窗口。
- private：服务实现、策略解析、请求状态、认证桥接、业务适配、审计/快照、数据库存储、导出和归档。
- 新功能统一使用项目专有 `qd.esign` 包和新增服务注册。禁止新增与产品同名同包覆盖类；禁止修改产品 JAR。

## 一次操作的事务边界

1. 客户端识别节点、按钮与选中业务对象，创建本次上下文；身份以服务端 NC 会话为准。
2. 策略服务决定是否签名、事由是否必填以及是否审计。总控及策略均由服务端重检。
3. 独立签名 RPC 验证当前用户并提交成功/失败/取消记录。签名 RPC 成功提交后才进入原业务 RPC，因此后续业务回滚不会删除签名成功记录。
4. 远程IOperationService使用tx=NONE编排，调用local-only IOperationTransactionService.claim的独立CMT，先提交RUNNING与仅服务端可见的execution_token，再进入业务CMT；原业务回滚不能把授权放回READY。
5. executeClaimed在业务CMT重新核验已认领状态、身份/BU、节点权威动作/对象类型、策略版本与独立总控版本；typed适配器保留原NC业务处理，同步hook采集前后快照。审计、差异、删除快照与业务写入在同一事务，审计失败向上抛出并回滚。
6. 新增编码回写取自真实持久化返回对象；批量逐对象关联，保留部分成功和待核对状态。
7. 客户端 `finally` 清理局部上下文；服务端线程上下文也必须 `finally` 清理。对于无回调、客户端退出等情况由持久化状态与补偿任务识别，不依赖静态全局变量。

外层捕获业务失败后由独立CMT记录失败，不能依赖客户端自报来消费授权；若失败状态也无法保存，则保持RUNNING阻断重放并显示明确故障，不释放READY。该多CMT边界已形成源码实现，真实NC容器代理传播、提交及故障回滚仍需环境验证。

不得虚构 `REQUIRES_NEW` 注册属性。已核验平台 TxAttribute 只有 CMT/BMT/NONE；签名独立性通过明确分开的 RPC 边界实现。真实事务是否生效必须在 NC 环境进行回滚测试。

## 适配策略

- UIF2 公共动作通过新增 `ActionInterceptorInfo` 加入现有拦截器组合，保留原拦截链。
- PF 单据在不覆盖产品类的前提下选择实际支持的上下文注入点及业务规则/事件注册；未证明完整跨 RPC 链前不启用该节点。
- 档案的主数据、子页、分配、批改、启停分别绑定实际动作及服务。
- 库存复合动作需要区分打开弹窗与最终保存/签字；一份授权关联真实生成的多张出入库单，避免重复签名或漏记。
- 数电发票涉及外部副作用时先保存请求；外部成功而本地回滚进入待人工核对，不自动重复调用。
- 安全事件独立接入平台实际安全/会话扩展入口；未验证注销、超时、锁定事件覆盖前明确列为未验证。

## 平台约束

`afterDoActionFailed` 必须保留原异常处理语义（本机 NCAction 字节码中返回 true 才继续原异常处理）。`afterDoActionSuccessed` 仅用于客户端状态收尾，不能直接制造成功审计。PF 的 `clear()` 会清理 eParam，因此“在 beforeDoAction 写 eParam”不构成有效上下文传递证明。详见 `SOURCE_MAP.md`。
