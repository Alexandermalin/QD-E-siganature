## 一、销售订单关闭管理：12 项

本机客户端配置为 `nc/ui/so/m30/closemanage/model/m30close_config.xml`；12 个 bean 均位于批量表格模型，分别配置对应的 `M30Close*Service`。下面的服务方法为本机接口/配置的静态线索，须核对实际加载类、服务端行为和恢复协议。

| 原表行 | 操作 / 按钮编码 | 客户端 bean | 原生服务方法线索 | 该项验收重点 |
| ---: | --- | --- | --- | --- |
| 217 | 整单关闭 `BillClose` | `billCloseAction` | `closeSaleOrder` | 整单及实际受影响行、关闭原因、下游单据检查。 |
| 218 | 整单打开 `BillOpen` | `billOpenAction` | `openSaleOrder` | 核对返回 `SOParameterVO[]`、原生继续确认及整单和行的恢复结果。 |
| 219 | 行关闭 `LineClose` | `rowCloseAction` | `closeSaleOrderRow` | 按授权的订单行逐一核对，未选行不得受影响。 |
| 220 | 行打开 `LineOpen` | `rowOpenAction` | `openSaleOrderRow` | 仅打开选中行；同单多行、已打开行和受下游限制的行遵循原规则。 |
| 221 | 发货关闭 `SendClose` | `sendCloseAction` | `closeSaleOrderSend` | 实际影响行的发货状态及数量约束。 |
| 222 | 发货打开 `SendOpen` | `sendOpenAction` | `openSaleOrderSend` | 已发货、下游占用与允许打开的不同分支。 |

| 224 | 出库打开 `OutOpen` | `outOpenAction` | `openSaleOrderOut` | 原生返回 `SOParameterVO[]` 的结果、继续确认及出库限制。 |
| 225 | 开票关闭 `InvoiceClose` | `invoiceCloseAction` | `closeSaleOrderInvoice` | 实际影响行、已开票数量及原生限制。 |

这些方法属于 `ISaleOrderCloseManageMaintain`，签名和返回类型并不一致：行开关使用 `SaleOrderViewVO[]`；整单打开和出库打开还涉及布尔参数并返回 `SOParameterVO[]`。不得把返回数组当作逐单成功回执。先确定每个 bean 的实际选择粒度、订单与行主键关系、开关原因、界面刷新、逐单任务及恢复确认，再决定可复用的受控入口。

为每个动作建立服务端固定白名单，绑定 `40060303 + 按钮 + 操作类型 + 订单主键 + 选中行主键集 + 组织 + 版本`。整单动作需验证实际影响的完整行集；行及发货、出库、开票、结算动作须核对实际影响粒度，不能按表格行号授权。对签名后选择变化、行归属变化、组织变化或版本变化的请求拒绝执行；是否允许部分行成功由原生事务和回执证据决定。关闭原因与签名事由各自保存。

现有 `ISaleOrderOperationAdapter` 的销售订单路线限定在 `40060301`；直接给 `40060303` 新增映射并不能证明其会走正确分支，甚至可能落入通用订单脚本。先评估在现有本地适配器中新增 **按节点区分的专用固定路由和类型化命令**，保持旧保存及 8 项按钮的判断不变；如果无法在已部署网关/事务下安全复用，再设计单独本地 CMT 适配器、UPM 和网关白名单。选择依据写入 S0，不能用客户端传入的方法名或仅靠按钮名分派。

## 四、共用设计与不可省略的条件

1. **取证先行。** 逐项输出「原表行/范围 ID → 功能/页签/按钮主键 → 实际加载的 XML 和动作类 → 页面选择及弹窗 → 最终 RPC/PF → 实现与事务 → 原生返回/刷新 → 回写/通知/外发」。区分 2026-11-07 静态快照、本机 JAR 和当前真实会话。核对三个节点的页签级注册、定制插件、交易类型、权限及对象组织；禁止凭源码候选自动标记为已实现。
2. **策略和身份。** 签名和审计的四种开关独立生效。以服务端当前会话和已持久化对象确定集团、业务组织、原生节点及按钮权限；同一授权主体必须满足按钮和组织，保留单据数据权限与当前审批工作项检查。新单据尚无持久化主键时绑定服务端可校验的集团、组织、交易类型、临时对象及请求，保存后以真实返回和落库单号关联。绝不能用当前登录组织代替单据的真实业务组织。
3. **固定路由与命令。** 关闭管理、发货、发票分别定义对象类型、DTO、动作白名单及服务器端固定委托。订单、发货和发票即使按钮同名也不能共享单一动作授权。不得由客户端传任意服务名、SQL 或 PF 名称；拒绝串节点、串动作、串对象、伪造组织、选择变化和重放。受控请求未支持的交易类型、额外参数、关联对象、流程分支或批量必须明确拒绝，不能降级到未受控的原生写入；明确不受控的已知组织按现有策略走原生路径。
4. **保留原生链路。** PF 动作核实 `PFlowContext`、交易类型、`PfUserObject`、审批意见/人员、校验器、单据转换、前后置规则和结果刷新。现有 `SaleOrderPfPreparation` 的固定类版本和适用动作不自动适配 4331/32；现有订单专用 VO/网关也不能直接装发货单或发票。先证明合约，再抽公共逻辑；需要独立接口时同时设计 UPM、网关白名单、打包及兼容性，保留现有 1.3.0 策略与销售订单补丁。
5. **行和聚合快照。** 首先只读核实三类单据的真实头/体/关联明细及字段白名单。订单现有 `OrderPhysicalSnapshots` 只覆盖订单和采购单，不能声称已覆盖发货或发票。新增读取器与受控事务连接，按真实主键/父子关系采集删除前、更新前后及新增后的实际落库快照，包含受影响的来源单回写、行状态和必要的流程证据；敏感认证字段不记录。删除与多行选择必须证明所有要求的关联明细齐全，缺失则审计开关下中止并回滚。字段级差异和日志标明真实节点、按钮、对象及行，不能仅写“操作成功”。
6. **事务与结果。** 原生业务、回写、成功审计及请求状态须验证属于同一事务；审计失败要让本地业务回滚。签名成功但业务失败，签名仍可查询，不产生成功业务审计。原生服务的正常返回、客户端回调、对象数组不自动证明真实成功；以动作对应的持久化状态、行关系和原生返回共同核对。已有共享批次/来源数据不得随单据删除。独立事务、消息或外发须逐项识别，不能声称本地回滚覆盖它们。
7. **批量和跨组织。** 最初只支持单个受控单据及其经核实的行范围。多选入口策略打开时，未适配批量应提示并拒绝，不回落原生写入；策略关闭的已知组织保持原业务。完整批量按需求实现一次认证、同批次每对象签名和真实结果；原生逐单提交时每对象拥有自己的业务与审计事务及成功/失败回执。核实同一订单多行、跨单、跨组织、部分成功、处理中断和重放。混合组织须有明确的组织分流及授权方案，不能拿一个组织覆盖全部对象。

## 七、构建、发布与并行协作

- 工作区已存在未提交的大量项目文件及其他会话改动，开工先记录逐文件哈希并协调文件所有权。不要清空 `build`、覆盖未归本批管理的文件，或以旧候选包覆盖已安装热修。隔离源码/输出目录适合离线试验，但最终须在冻结的实际交付源码上重跑。
- 主工程使用 `powershell -NoProfile -ExecutionPolicy Bypass -File tools/build.ps1 -Test` 和其验证记录，新增测试纳入 `AllTests`。当前工作区曾因并行写入造成构建输入漂移；安排串行冻结窗口后重建，记录源码、依赖、测试及产物哈希。独立兼容构建需要明确新增源码、测试、UPM、白名单及资源是否被纳入，不因旧销售订单兼容包构建通过而认为本批已编译。
- 基于部署时实际 HOME 文件做增量兼容包，复核现有 `SaleOrderPilotPolicyService`、已安装销售订单补丁、网关接口、UPM 和现有业务 JAR。需要更改公共网关或服务白名单时，逐项说明兼容风险和回归；比较本批包与基线的每个 JAR 条目，并检查内部类及配置资源。
- 先生成按节点/按钮的只读预检、事务性映射、验证和撤回脚本草案。核对目标数据库、schema、版本、集团、组织、原有策略、节点/按钮注册、适配器、当前运行和未知结果的请求及原值；不自动提交，不批量开启组织总控。脚本与候选源码/清单一起审阅。
- 真实实施由负责人安排共享测试环境窗口：备份 → 核对包与目标哈希 → 策略关闭跑原生基线 → 隔离联调 → 按通过的按钮及组织逐项启用。撤回时停止新请求，核对正在处理及未知结果，只撤回本批策略、映射和文件；保留订单、发货单、发票和已有签名/审计证据，不覆盖后续补丁。
- 项目本轮规则为先离线开发，SQL 仅生成、执行前确认。未经另行安排，不部署或启用、执行数据库写入、启停共享 NC 或触发真实外部平台。真实联调要使用清晰标识的测试数据并记录影响。
