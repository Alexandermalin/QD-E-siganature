# 销售订单其他按钮电子签名开发计划

交接对象：DeepSeek。基线日期：2026-11-11。实施对象是 NC65「销售订单维护」`40060301`。先在 990 销售组织验证单张普通订单，按原生入口补齐正式清单第 209–216 行共 8 项，再补齐现场确有的多选和复合路径。每个入口须通过真实 NC 联调，才可计入完成。

## 范围和保存基线

- 第 208 行 `Save / INSERT` 是已有的手工新增保存试点。本次保留该实现和空收款容器兼容修复，回归「保存」「保存并提交」以及普通订单之外的原生入口，不扩展复制、参照生成、修改保存、收款结算或抵消。原生「保存并提交」复用提交 bean；接入提交时必须覆盖该提交入口的策略和回归，见下文。
- 第 217–228 行是独立的「销售订单关闭管理」`40060303`。即使它与本节点共用整单关闭服务，客户端、按钮权限和策略也分别核对；这 12 项另排。发货单、销售发票、工作台审批及自动接口不在本批。
- 首轮组织：集团 `0001A9100000000005MH`、990 销售组织 `0001A9100000003UDS6R`。以订单实际销售组织判断。已确认在 990 之外的订单继续走原生路径；无法确认归属、混合组织、策略查询失败或受控分支无法验证时，禁止通过原生写入绕开签名。扩大组织另做策略、权限及接口评估。
- 现场兼容包以 QDNC 1.3.0 已有项目文件为基线。开发 HOME 有保存补丁的文件发布记录（`build/deployment/20261111-100853-135cd831/sales-file-only-journal.json`）；空收款容器修复回执（`build/sales-990-balance-fix/stage-20261111-140357-5be4f8b7/publish.json`）中的 `new_sha256` 与当前本机销售服务 JAR 一致。文件证据不能证明 QDNC 当前映射、策略、客户端实际加载类或事务验收状态。开工时冻结当前目标 HOME 的文件与配置，不用早先的 ZIP 覆盖热修。

## 八项操作与实现落点

下表按钮编码和注册主键来自 [现场按钮快照](site-evidence/2026-11-07/buttons_1.json)，bean、类及脚本来自本机 `uiso_salesorder.jar` 的原始 `saleorder_config.xml` 和字节码。它们是定位起点；每个入口还须核对当前 NC 会话加载的类、最终写入调用及原生分支。范围 ID 保留 [正式清单](../../config/qd-esign/operation-scope.csv) 的值。

## 公共接入方式

1. **客户端。** 扩展 [QdSaleOrderConfig.xml](../../uapbd/src/client/nc/ui/uapbd/qd/esign/QdSaleOrderConfig.xml) 的销售专用覆盖层，保留产品 XML、bean 属性、列表/卡片选择、异常处理、进度与刷新。先复用原生输入和取消路径，在即将发起真实写入时复用 `ElectronicSignatureActionInterceptor` 的签名窗口与请求交接契约；无需签名且审计关闭时保持原生调用。签名动作与授权对象在窗口关闭后重新核对。受控路径只把一个类型化命令交给 `IOperationService`，不在成功后再调一遍原生写入。
2. **销售服务。** 优先复用已在兼容包网关白名单中的 [ISaleOrderOperationAdapter](../../so/src/public/nc/itf/so/qd/esign/ISaleOrderOperationAdapter.java) 和本地 CMT 注册。现有适配器除保存路由外只支持按 `INSERT/UPDATE/DELETE` 委托低层脚本服务，不能直接接新按钮。为已核实的节点、按钮、对象类型和操作类型定义固定分支及 DTO；服务端决定原生方法，客户端不传可执行的类名、SQL 或任意脚本名。默认在映射中将删除归类为 `DELETE`、其余状态变更归类为 `UPDATE`，以复用现有快照分支，并在日志中用真实按钮编码和名称区分业务动作。若验收要求独立的动作类型，先验证快照、差异、查询和兼容包影响，单列改动，不用通用 UPDATE 分支兜底。
3. **授权与并发。** 首轮限定一张 `SO_SALE_ORDER`。服务端以当前 NC 会话和查库得到的订单主键、集团、销售组织、版本为准；校验功能、按钮及组织处于同一授权主体，并保留对应的原生数据权限和审批工作项权限。用原生锁/版本规则与同事务快照约束执行对象，审计关闭时也要拦住换单、换组织、流程任务变化及过期授权。审批决议、流程任务、继续确认和关闭原因采用按动作定义的参数白名单；在确认后禁止替换关键输入。若现有请求无法绑定必要的流程上下文，先交付有测试的绑定设计和最小变更；仅验证客户端对象不足以启用该分支。
4. **原生 PF。** 删除、提交、收回、审批和取消审批保留完整 PF 路径：原交易类型、前置提示/校验、`PfUserObject`、流程参数、真正写入的 RPC、结果处理和后置插件。 `PFlowContext` 会被清空；不能只在 `beforeDoAction` 塞参数。优先核实可注入的最终调用点；保存的 `SaleOrderPfPreparation` 只验证了固定版本的 `WRITE`，不能套到 `SAVE` 或 `APPROVE`。若必须做版本限定的桥接，应逐动作验证客户端契约、类来源及哈希，并对未识别版本拒绝受控执行。不得直接用 `saleOrderDelete` 或审批底层接口代替未证实等价的 PF。
5. **审计与恢复。** 复用 [OrderPhysicalSnapshots](../../uapbd/src/private/nc/bs/uapbd/qd/esign/audit/OrderPhysicalSnapshots.java) 和审计链，先核实现场兼容包能识别该适配器及操作类型；现有销售快照只读订单头和表体，删除前另核实受影响的关联明细，审批另核实工作项和状态证据。用服务端实际落库值按稳定主键比较，记录真实单号、签名、请求、快照和字段差异。删除确认原对象实际消失或失效；流程动作以原生结果和持久化流程推进为准，不能把成功回调、返回原 VO、无变化或未提交当成业务成功。业务、成功审计和请求终态在同一业务事务；原生失败或审计写失败不留成功审计，已提交的签名可独立查询。重复提交只查已知结果；超时/回包丢失先查请求及原单状态。原生继续确认如需重新执行，仅在已证实前次无业务写入时走新的授权；结果不明或已有外部副作用时挂待核对。
6. **策略和共存。** 扩展 `SaleOrderPilotPolicyService` 仅允许已核实的新范围及原保存范围在 990 开启，同时在销售服务端再次限制集团、组织和动作。保留现有物料归属策略、日志/认证和已装网关。核对 V1 `PluginBeanConfigFilePath`（`saleorder_esign_probe.xml`）、`PluginBeanConfigFilePath_Industry0_tempsave`、交易类型定制及审批后置插件是否实际生效；参考 HOME 存在向 OA 发消息的审批拦截代码。由现场确认是否有 OA、APS 或其他外发及独立事务，成功回调须在可确认的原生成功后执行。无法证明不漏发、不重复、不在回滚后误发时，对应入口保持关闭。

「保存并提交」按两个原生动作验收：`Save/WRITE` 保存成功并返回真实单据后才进入 `Commit/SAVE`，分别按各自按钮策略执行；两个开关都要求签名时，各自授权一次，不复用保存授权。提交取消或失败时，已经成功的保存结果及其审计保留，界面能说明订单仍未提交；保存取消、失败或结果未知时不得触发提交。重点测试原生复合动作判断条件（本机只检查退出编辑状态），防止误提交旧选中订单。

如果同一按钮还支持多选，单笔联调只用隔离样本并明确拒绝未适配的受控多选。启用按钮策略后，多选不能绕回原生写入。共享环境需要同时支持单笔和多选时，先通过 S5，再开启该按钮。

## 联调矩阵和完成标准

每项至少跑一次自己的成功、取消、原生拒绝、审计写入故障和策略关闭场景；列表、卡片或弹窗走不同写入路径时分别跑。同一批次可共用环境准备，不能用一个按钮的成功推定另一个按钮的事务。

| 场景 | 要核对的结果 |
| --- | --- |
| 签名、审计四种组合 | 开/开：二次认证、真实业务及关联日志；开/关：只留签名证据；关/开：无密码窗，业务与审计同提交；关/关或组织总控关闭：原生业务，无新增普通签名/审计。 |
| 必填事由、错密、关闭签名窗 | 留空按策略拦截；错密复用原生次数/锁定；取消只产生一次取消记录。均不执行订单写入。 |
| 权限和对象变化 | 仅有节点权限、无原数据权限或审批任务权限不能写；非 990 已知订单保持原生。篡改订单、签名后换单、切组织、并发改版、策略关闭后重放均须拒绝，且不降级到无签名写入。 |
| 故障、双击和回包丢失 | 受控重复请求不重复执行。签名成功后原生拒绝，签名可查询且无成功审计。在隔离环境于原生返回后、审计提交前注入故障，从独立会话核对订单、工作项和审计共同回滚；有外发的动作另核对副作用。 |
| 日志和界面 | 从真实单号找到请求、签名、审计、差异及快照，反向能定位同一业务对象；查询与导出受原权限限制。保留原生按钮显隐、确认、审批结果、错误信息和刷新行为；日志不含密码、凭证或任意流程载荷。 |
| 已有保存与其它节点 | 用 990 普通手工新增单（含原生初始化的空收款容器）验证保存；按基线测试关闭/切换窗口、保存并提交、其他组织、暂存及原生非试点场景；物料归属策略与关闭管理节点运行不受影响。 |

每条证据记录：原表行/范围 ID、实际入口和按钮编码、交易类型、组织、测试角色、订单号、请求号、签名及业务终态、审计编号、原生调用次数、前后状态、外发结果、候选包哈希及证据位置。维护 [任务台账](TASK_TRACKER.md)、[测试报告](TEST_REPORT.md) 和 [待解事项](UNRESOLVED_ISSUES.md)。编译、XML 加载和模拟测试可证明候选可交付；真实 NC 认证、原生流程、同事务回滚和权限验证齐全后，才标记「已完成并通过实际测试」。只有单笔证据时标明单笔覆盖及仍待验收的入口。

2. 当前本机 `qd_esign_core.upm` 已指向 `SaleOrderPilotPolicyService`；旧打包脚本假设它仍指向 `PolicyServiceImpl`。候选脚本要显式验证并支持当前基线，已正确绑定时保留 UPM，发现未知状态中止。既有文件发布工具同样有固定变更清单；为本批核对清单和回滚测试，不套用旧补丁的部署 ID。主工程整包用于离线核验，不能替代现场 1.3.0 的增量包。
3. 另写八项的只读预检、映射和撤回脚本草案。参照 [990 保存兼容脚本](../../sales-order-990-release/sql/nc65-electronic-signature/sale-order-save-pilot/configure.sql) 核对环境、版本、节点/按钮主键、适配器、旧行、策略和运行中请求；严格限定行号和组织，无隐式提交，不替换原保存映射、插件参数或总控。不凭离线测试预设「已验证」。需用临时 `PILOT/Y` 开展真实联调时，只在获准的测试范围内逐项配置，保留回退前值和取证。
4. 现场顺序：冻结包与目标文件 → 备份 → 保持新增策略关闭验证原生基线 → 隔离联调 → 按通过的按钮逐个开启 990 策略。撤回时先停止新请求、只停本批策略并核对运行中和结果未知的请求，再恢复本批映射、节点配置及文件备份。保留已有保存、物料策略和签名/审计记录；发现之后有其他修改时先重新比对，不能直接用旧备份覆盖。

DeepSeek 的本批交付为源码、测试及候选脚本和回退说明。真实部署、注册/数据库写入、启动或停止共享 NC 及实际外发由项目负责人安排测试窗口执行。
